01

Locked decisions

These are settled and drive everything below.

  1. 1 · Fully air-gapped / self-contained. No build-time dependency on any Hitachi-hosted artifact. Every upstream Pentaho library (mondrian, reporting, kettle, common-ui, commons-*, osgi-bundles, metadata …) must be forked, built on JDK 17, and hosted in your own Nexus. A multi-repo program — §5.
  2. 2 · Do not rename Java packages. org.pentaho.* stays. Keeps reflection, Spring XML class=, GWT modules, ServiceLoader descriptors and plugin APIs intact; keeps future upstream merges tractable.
  3. 3 · Existing content repositories upgrade in place. Not greenfield. Constrains JCR namespaces, Spring bean ids, and the solution-tree layout to stay compatible. Upgrade must be drop-in.
  4. 4 · Namespace different from Pentaho — for Maven coordinates, distribution names, product branding. Not Java packages (decision 2), not JCR namespaces (decision 5). Reactor → com.helix.platform / helix-platform-*; pentaho-solutions → helix-solutions; product name → “Helix”.
  5. 5 · Keep JCR namespaces pho / pho_nt / pho_mix as-is (http://www.pentaho.org/jcr/2.0). Internal, invisible to users; no Jackrabbit migration; in-place upgrade just works.
  6. 6 · Squash git history. Orphan base commit (10.1 tree) + one squashed commit for the 10.1→master-0718 delta, then rebrand commits on top. No 954-commit replay.
Consequence The forked upstream libraries are vendored, not rebranded. Only pentaho-platform itself becomes Helix. The ~20 dependency repos keep their org.pentaho* coordinates and packages — you just build and host them. That keeps the dependency program to “build & host” rather than “build & rebrand & host”.

Naming to fix now

  • Maven groupId: com.helix.platform — distinct from the org.pentaho Java packages, which stay
  • Artifact prefix: helix-platform-*; distribution: helix-server, helix-solutions, helix.war
  • Product display name: “Helix” / “Helix Platform”
  • Env vars / system properties: PENTAHO_* → HELIX_*, with back-compat fallbacks so in-place upgrades keep working

Mechanics

  • Case-preserving replacement (Pentaho→Helix, pentaho→helix, PENTAHO→HELIX), scripted, per category, never one global sed.
  • Order: file contents first, then git mv paths, then directories; commit in reviewable slices.
  • Exclusion list (never rewrite): JCR pho* prefixes & http://www.pentaho.org/jcr/2.0; http://www.pentaho.com/schema/pentaho-system; http://reporting.pentaho.org/namespaces/*; vendored upstream Maven coordinates (org.pentaho.*, pentaho-kettle:*, org.pentaho.reporting.*); Java package / import statements.
  • Guardrail: full build + IT suite green before and after each slice; keep a read-only pentaho-platform mirror to diff against.

Execution plan

  1. 0

    Infra & confirmation

    • Private Git remote; Nexus with a hosted release repo (helix-releases) and no external proxy.
    • CI runners: JDK 17 (primary) and JDK 21.
    • Confirm source availability of com.hitachivantara.security.web:* and org.hitachivantara.karaf.assemblies. Fork / vendor-binary / replace decision per artifact.
    • Legal sign-off: LGPL-2.1 / GPL-2.0 fork, copyright-notice handling, “Helix” trademark clearance.
    • Finalise names from §6.
    blockingno platform code
  2. 1

    Seed the private repo (squashed)

    # orphan base at the 10.1 tree
git init helix-platform && cd helix-platform
git --git-dir=/path/to/pentaho-platform/.git archive 10.1 | tar -x
git add -A && git commit -m "Baseline: pentaho-platform 10.1 (squashed)"
git tag helix-base-10.1

# one squashed commit bringing the tree to master-0718
git --git-dir=/path/to/pentaho-platform/.git archive master-0718 | tar -x --overwrite
git add -A && git commit -m "Import trunk 10.1..master-0718 (954 commits squashed)"
git tag helix-import-11.1

git remote add origin <private-url> && git push -u origin main --tags

    Attach commits-after-10.1-full.txt to the second commit message or a PROVENANCE.md so the squashed history stays auditable.

    ~1 day
  3. 2

    Resolve & fork the dependency graph

    • Build the master-0718 tree once against Hitachi Artifactory, clean ~/.m2.
    • Capture the authoritative fork list: dependency:tree / dependency:list filtered to pentaho|mondrian|hitachivantara, deduped to groupId:artifactId.
    • Fork each source repo (§5), bottom-up. Per repo: repoint parent POM + <repositories> to Nexus, build on JDK 17, publish to helix-releases (keep original coordinates; optional -helix.1 suffix).
    • Pinned legacy jars that never change (pentaho-cwm, pentaho-vfs, pentaho-concurrent, simple-jndi): vendoring the released binary is acceptable.
    • Success test: mvn -o (offline) builds the platform tree end to end with zero hits to any hitachivantara.com host.
    the long pole~4–8 months
  4. 3

    Own the platform build config

    • Replace pentaho-ce-jar-parent-pom with helix-platform-parent (fork of maven-parent-poms, or a thin parent that <parent>s your mirrored copy).
    • Reactor coordinates → com.helix.platform:helix-platform-*; <scm> / <url> → Helix.
    • CI green on JDK 17 and 21; full IT suite (-DrunITs) baseline recorded.
    ~1 week
  5. 4

    Rebrand in reviewable slices

    One commit/PR per slice, build + IT between each:

    • 4a Maven artifact + assembly names (pentaho-solutions→helix-solutions, pentaho.war→helix.war, pentaho-server→helix-server).
    • 4b Runtime paths, start scripts, system properties, web.xml context, license-path env var (with PENTAHO_* back-compat fallbacks for in-place upgrade).
    • 4c UI branding: logos, favicons, About / login, pentaho-style / user-console CSS.
    • 4d i18n sweep of 667 messages*.properties — user-visible strings only.
    • 4e URLs & doc links → Helix (respecting the §6 exclusion list).
    • 4f License headers: add Helix copyright, preserve Pentaho / HV notices; update license/templates + per-module LICENSE.txt.
    ~2–4 weeks
  6. 5

    Upgrade path & release

    • Build full helix-server assembly; boots on Tomcat 10 / JDK 17.
    • In-place upgrade test (decision 3): stand up a real Pentaho 10.1 server with content (reports, schedules, ACLs, data sources) in its Jackrabbit repo → deploy Helix over it → verify login, repo browse, run report, run transformation, run schedule, import/export round-trip. This is the acceptance gate.
    • Security + license scan (FOSSA / Snyk) on the closed tree.
    • Document the upstream-merge procedure: read-only pentaho-platform remote, git merge -X strategy, the §6 exclusion list as a .gitattributes merge-driver config, cadence for pulling upstream security fixes.
    ~3–4 weeks
Order of magnitude Platform fork + rebrand (packages & JCR untouched): ~6–9 weeks, one engineer who knows the platform. Air-gap dependency program (§5, 15–25 repos): ~4–8 months, small team, partly parallel. In-place-upgrade hardening: ~3–4 weeks. The air-gap program dominates — if it can be de-scoped to “private source + frozen Nexus mirror” the whole thing compresses to ~8–12 weeks. Worth re-confirming “air-gapped” is a hard requirement.
